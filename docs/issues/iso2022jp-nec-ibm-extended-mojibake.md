# ISO-2022-JP本文がNEC選定IBM拡張漢字を含むと丸ごと文字化けする問題

## 発生日・関連コミット

- 発見日: 2026-08-18
- 該当実装: [charset.py](../../src/mail_dock/infrastructure/parsing/charset.py) の `decode_text()`
- 実例: `s-mghk03@kyoto-daiken.co.jp` 宛メール（Outlook/Exchange経由、`X-MS-Exchange-*` ヘッダーあり）

## 症状

`charset="iso-2022-jp"` と宣言された本文が、アプリ上で本文**全体**が次のような形で文字化けして表示された。

```
□$B3t<02q<R5~ET%@%$%1%s%S%k%5!<%S%9□(B
```

`□`はESC制御文字（`0x1B`）がフォントで表示できず四角になったもの、`$B`/`(B`はISO-2022-JPのエスケープシーケンス（本来は解釈されて消えるべき部分）がそのまま文字として見えている状態。1文字の未対応文字が原因で**本文全体**が読めなくなっていた。

Thunderbird等の一般的なメールクライアントでは同じメールが問題なく表示できることを確認済み。

## 原因

1. 本文中に **NEC選定IBM拡張漢字**（cp932のリードバイト`0xFA`〜`0xFC`帯、ISO-2022-JPの区（ku）89〜92の領域）に属する文字が1文字含まれていた。実例では区89・点85の文字（バイト列`b"yu"` = `0x79 0x75`）。日本語の人名・地名でよく使われる`髙`（はしごだか）や`﨑`（たつさき）もこの領域に属する代表的な文字。
2. Python標準ライブラリの `iso2022_jp` / `iso2022_jp_ext` コーデックは、このNEC選定IBM拡張漢字の区をどちらも**サポートしていない**。該当バイト列に対して両方とも `UnicodeDecodeError`（`illegal multibyte sequence`）を送出する。
3. 修正前の [charset.py](../../src/mail_dock/infrastructure/parsing/charset.py) は、`iso-2022-jp` → `iso2022_jp_ext` が失敗すると次善策として `cp932` の strict デコードを試みていた。ところが本文のバイト列はISO-2022-JPのエスケープシーケンス由来で**すべて0x7F以下（7bit ASCII範囲）**であるため、`cp932`はこれを**エラーなく**1バイトずつのASCII/JIS-Roman文字列として「デコード成功」してしまう。その結果、ESCシーケンスや2バイト漢字コードが変換されずにそのまま文字として漏れ出し、本文全体が文字化けする。
4. この文字はそもそも標準ISO-2022-JP（JIS X 0208）の範囲外であり、本来は`iso-2022-jp-ms`のような拡張ラベルで送るべきだが、実例の送信元（Outlook/Exchange）は`iso-2022-jp`のまま送出していた。これはWindowsが内部的にcp932でUnicode→バイト列変換した結果を、そのまま`iso-2022-jp`ラベルで送出してしまう、日本語Windows環境で古くから知られる「機種依存文字によるメール文字化け」の一種。

## 根本原因の特定手順（再現性のある調査レシピ）

1. `BytesParser(policy=policy.default)` でパースし、対象パートの `get_payload(decode=True)` で生バイトを取得する（CTE=quoted-printable等のデコード済み）。
2. `payload.decode("iso-2022-jp")` / `"iso2022_jp_ext"` を試し、`UnicodeDecodeError.start` で失敗バイトオフセットを特定する。
3. 失敗位置の2バイト `b0, b1` から `ku = b0 - 0x20`, `ten = b1 - 0x20` を計算する。
4. `ku`が13ならNEC特殊文字、89〜92ならNEC選定IBM拡張漢字と判定できる。

## 対応方針と実装

**方針:** 本文全体をcp932に丸投げするのではなく、宣言charsetが`iso-2022-jp`系のときだけ、未対応文字だけを`U+FFFD`（�）に置き換える「豆腐化」で救済する。読める部分は読めるまま表示し、本アプリはEMLアーカイブが主目的でThunderbird等の定評あるクライアントでの完全な閲覧を代替手段として許容する、という前提に立った現実的な折衷案。

**実装 (`decode_text()` in [charset.py](../../src/mail_dock/infrastructure/parsing/charset.py)):**

- 宣言charsetが`iso-2022-jp`/`iso2022_jp_ext`に正規化される場合のみ、両コーデックのstrictデコードが失敗した後、**`cp932`を試す前に** `iso2022_jp_ext` を `errors="replace"` でリトライする（`_decode_lenient`）。
- 置換文字（`U+FFFD`）の比率が **5%を超えたら不採用** にし、通常のフォールバック（`cp932`等）へ戻す安全弁を設けた。これにより、本当に丸ごとcp932で書かれたメールを`iso-2022-jp`と誤宣言しているケース（既存の想定シナリオ）まで文字単位で破壊することを防いでいる。
- **cp932は7bit範囲のバイト列に対して絶対にエラーを出さない**ため、救済ロジックをstrictループの「後」ではなく、cp932を試す**直前**に挟む必要がある。最初の実装ではこの順序を誤り、cp932が先に（誤って）“成功”してしまい救済が発動しないバグを作り込んだ。テストで発覚し、順序を修正した。

## テストで得た教訓

- **比率ベースの安全弁をテストするときは、実際のメール本文程度の長さのサンプルを使うこと。** 4文字程度の短い合成テキストに1文字の不良文字を混ぜると置換比率が25%になり、5%のしきい値で正しく弾かれてしまう（本来救済したいケースなのに）。テストは本文を数十〜数百文字に伸ばして、現実的な比率になるようにする。
- **cp932は0x00〜0x7Fの範囲のバイト列に対して常にエラーを出さない。** ISO-2022-JPのエスケープシーケンスやJIS X 0208の7bitコードはすべてこの範囲に収まるため、フォールバックチェーンで`cp932`を`iso-2022-jp`系コーデックより後に置いても、「先に試して失敗したら次へ」という単純なfor-loopの実装では、救済ロジックの挿入位置を誤ると本来の意図と逆の結果になる。コーデックの「エラーを出さない」特性は「正しくデコードできた」ことを意味しない、という前提を常に忘れないこと。

## 既知の限界・今後の検討事項

- NEC選定IBM拡張漢字（区89〜92）およびNEC特殊文字（区13）は、Python標準ライブラリのどのISO-2022-JP系コーデックでもデコードできない。豆腐化以上の完全な復元は、独自のコードポイント変換テーブルを実装しない限り不可能。
- 同じ文字が`cp932`として正しく宣言されていれば問題なくデコードできる。文字化けの根本原因は常に「送信側の誤ラベリング」であり、受信側の完全な解決策は存在しない。
- `﨑`（U+FA11）を含む実メールはまだ入手できていない。入手できれば同じ手順で区点を確認し、本ドキュメントに実例として追記する。
